# Мини-ТЗ: уведомления и журнал действий

Ветка второго бэкендера после статей. Основная логика (соревнования — [007_tz_contests.md](007_tz_contests.md)) здесь не трогается.
Правила — [000_conventions.md](000_conventions.md). Это общий фронт работы: детали, пагинация, фильтры, тексты — на усмотрение исполнителя. Фронтенд не трогается.

## Зачем

- Кейс требует уведомлений о ключевых событиях в кабинете и минимум в одном внешнем канале. Канал — email.
- Журнал действий пишется с первого этапа (`audit_log`), но посмотреть его сейчас нельзя.
- Это инфраструктура: другие модули (соревнования, заявки, разряды) потом шлют уведомления одной строкой.

## Часть 1. Уведомления

### Модель
`infrastructure/notification.py` — `NotificationModel`: кому (`user_id`), тип события (строка, например `role.approved`), заголовок, текст, ссылка во фронт (необязательно), прочитано ли, когда создано; для письма — статус отправки и время.

### Область `backend/notifications/`
- Доменный класс `Notifications` (без слова «сервис»): `notify(user_id, type, title, text, link=None)` — создаёт уведомление в той же транзакции, что и действие.
- Слать ли письмо, решает **сам класс** по типу события: у него список `EMAIL_TYPES`. Вызывающий модуль флаг письма не передаёт — так никто случайно не заспамит, а список писем правится в одном месте.
- Отправка писем — фоново после коммита, с повторами; ошибка письма не ломает основное действие.
- Пользоваться из других областей — только через этот класс.

### Какие события уходят письмом
Правило: письмо — только когда **чужое решение изменило твою ситуацию**, когда **горит срок** или это **вопрос безопасности**. Всё остальное — только колокольчик в кабинете. Журнал действий (`audit_log`) никаких уведомлений и писем не порождает.

| Событие | Кому | Кабинет | Письмо |
|---|---|---|---|
| Сброс пароля | пользователь | — | да, всегда |
| Роль подтверждена / отклонена | пользователь | да | да |
| Соревнование верифицировано / в верификации отказано / верификация снята | организатор | да | да |
| Соревнование отменено (будущее, когда появятся заявки) | участники | да | да |
| Заявка на участие одобрена / отклонена (будущее) | спортсмен, тренер | да | да |
| Разряд или судейская категория присвоены / отклонены (будущее) | спортсмен, судья | да | да |
| Скоро истекает разряд или категория (будущее, пороги 30 / 7 дней) | владелец | да | да, одно письмо на порог |
| Новая заявка на роль, новое соревнование на согласование | федерация | да | нет — их много, федерация разбирает очередь в кабинете |
| Открылась регистрация, опубликован протокол (будущее) | участники | да | нет |
| Всё, что человек сделал сам | — | нет | нет |

### Эндпоинты (сессия, только свои уведомления)
| Метод | Путь | Что делает |
|---|---|---|
| GET | `/notifications` | лента, новые сверху; фильтр «только непрочитанные», пагинация |
| GET | `/notifications/unread-count` | число непрочитанных — для колокольчика |
| POST | `/notifications/{id}/read` | отметить прочитанным |
| POST | `/notifications/read-all` | отметить все |

Чужое уведомление → 404.

### Email
- SMTP. В контейнер добавляется Mailpit: принимает письма локально и показывает их в веб-интерфейсе (порт пробросить в `manage/fsp.py`), чтобы на демо было видно реальную отправку.
- Настройки SMTP — в `core/config.py`.
- Простые текстовые / HTML-шаблоны писем.

### Первые реальные события
- Решение федерации по роли (подтверждена / отклонена с причиной) → уведомление пользователю + письмо.
- Сброс пароля → письмо со ссылкой (вместо записи в лог).
- Остальные события (соревнования, заявки, разряды) подключают владельцы этих модулей после слияния.

## Часть 2. Журнал действий

### Эндпоинт (только федерация)
| Метод | Путь | Что делает |
|---|---|---|
| GET | `/admin/audit` | записи журнала, новые сверху; фильтры: пользователь, действие, тип объекта, период; пагинация |

В записи: время, кто (id, ФИО, email), действие с понятным русским названием, объект, подробности (`payload`), IP.

## Пересечения
- Правится `auth`: 2–3 строки в `Roles` и `Account` — вызов уведомления. Больше в чужие области не лезем.
- `manage/Dockerfile`, `manage/entrypoint.sh`, `manage/fsp.py` — Mailpit.
- Общие файлы (`main.py`, `bootstrap.py`, `errors.py`, `config.py`, `001_api_map.md`) — дописываем, конфликты решаем при слиянии.

## Готово, когда
- Федерация подтверждает роль → у пользователя появляется уведомление в кабинете и письмо в Mailpit.
- Письма уходят только по типам из `EMAIL_TYPES`; уведомления федерации о новых заявках на роль — только в кабинете.
- Сброс пароля приходит письмом.
- Колокольчик: счётчик непрочитанных, отметка прочитанным, «прочитать всё».
- Федерация смотрит журнал действий с фильтрами.
- Раздел в `docs/001_api_map.md`, pyright — 0 ошибок, контейнер собирается.
