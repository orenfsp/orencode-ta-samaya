# ТЗ: уведомления, письма и журнал действий

Ветка `Andrey-5`. Правила — [000_conventions.md](000_conventions.md), фронт — [frontend/RULES.md](../frontend/RULES.md), контракт — [001_api_map.md](001_api_map.md), разделы «Уведомления» и «Журнал действий».

## Зачем

- Кейс требует уведомлений о ключевых событиях в кабинете и минимум в одном внешнем канале. Канал — email.
- Журнал действий (`audit_log`) пишется с первого этапа. Федерации нужен экран, где его можно разобрать.
- Это инфраструктура: любой модуль шлёт уведомление одним вызовом в своей транзакции.

## Часть 1. Уведомления

### Модели

`infrastructure/notifications/notification.py` — `NotificationModel`, лента кабинета:

| Поле | Тип |
|---|---|
| id | uuid |
| user_id | uuid fk users, cascade |
| type | str(100), код события из каталога |
| title | str(200) |
| text | text, простой текст с абзацами, HTML не исполняется |
| link | str(1000) null, внутренний путь сайта |
| is_read | bool |
| email_status | enum `email_status`: `not_required` / `pending` / `sent` / `failed` |
| email_sent_at | timestamptz null |
| created_at | timestamptz, индекс `(user_id, created_at)` |

`infrastructure/email_outbox.py` — `EmailOutboxModel`, очередь писем: получатель, тема, текст, ссылка, статус `pending` / `sending` / `sent` / `failed`, число попыток, время следующей попытки, аренда (`lease_token`, `leased_until`), срок годности (`expires_at`, только для сброса пароля), последняя ошибка (имя класса исключения).

### Область `backend/notifications/`

```
domain/types.py            NotificationType — каталог событий
domain/notifications.py    Notifications — создание уведомлений, тексты, решение о письме
domain/letter.py           Letter — письмо в стиле ФСП (HTML + текст)
domain/mail_worker.py      MailWorker — фоновая отправка очереди
repositories/pg_notifications.py, pg_outbox.py; clients/smtp.py
features/inbox/            лента текущего пользователя
dependencies.py            NotificationsDep, mail_worker()
```

- `Notifications.notify(user_id, type, title, text, link=None)` создаёт уведомление в текущей транзакции. Commit не делает, SMTP не трогает.
- Слать ли письмо, решает **сам класс** по `EMAIL_TYPES`. Вызывающий модуль флаг письма не передаёт.
- Для каждого события из каталога есть типизированный метод (`contest_verification`, `application_decided`, …). Он принимает примитивы: id, названия, причину. Тексты всех уведомлений живут в одном месте.
- Инициатор события уведомления о своём действии не получает. Получатели без дублей. Неактивные пропускаются.
- Ссылка — только внутренний путь: начинается с `/`, без `//`, `\`, схемы и управляющих символов, до 1000 символов. Нарушение — `ValueError`: это ошибка программиста, а не пользователя.
- Ссылка в кабинет организатора вычисляется по подтверждённым ролям получателя: организатор → `/cabinet/organizer/...`, иначе федерация → `/cabinet/federation/...`.

### Какие события уходят письмом

Письмо — только когда **чужое решение изменило твою ситуацию**, когда **горит срок** или это **вопрос безопасности**. Всё остальное — только кабинет. Журнал действий уведомлений не порождает.

### Как подключить новое событие

1. Код — в `NotificationType`.
2. Метод в `Notifications` с текстом и ссылкой. Если по правилу нужно письмо — тип в `EMAIL_TYPES`.
3. В домене: `NotificationsDep` в `dependencies.py` области, вызов метода **до** `uow.commit()`. Откат транзакции отменяет и уведомление, и письмо.

### Отправка писем

- Очередь — таблица `email_outbox`, пишется в той же транзакции, что и действие.
- `MailWorker` запускается в lifespan приложения (`FSP_MAIL_WORKER_ENABLED`). Раз в 5 с берёт до 20 заданий через `FOR UPDATE SKIP LOCKED`. Аренда — 300 с, фиксируется до SMTP. После падения процесса задание снова доступно по истечении аренды.
- До пяти попыток: сразу, через 30, 120, 300 и 900 с. После пятой — `failed`. Таймаут SMTP — 10 с.
- `sent` — письмо принял SMTP-сервер. Гарантия — at least once: после принятия письма, но до фиксации успеха возможен повтор. Message-ID у повторов одинаковый.
- Сброс пароля: только задание на письмо с `expires_at`. Ссылка не пишется в аудит и логи. После отправки или отказа текст и ссылка из задания стираются. Просроченное задание закрывается без SMTP.
- Ошибка письма не ломает основное действие и не откатывает его.

### Письмо

Класс `Letter`: `multipart/alternative`, текст + HTML с инлайн-стилями, без картинок и внешних ресурсов.

- Шапка: «ФСП Оренбургской области» моноширинным, тонкая линия.
- Заголовок события, текст абзацами, кнопка `#402fff` с белым текстом: «Открыть» или «Задать новый пароль».
- Под кнопкой — та же ссылка текстом.
- Подвал серым: «Письмо отправлено автоматически, отвечать на него не нужно.»
- Все значения экранируются. Абсолютная ссылка = `FSP_FRONTEND_URL` + внутренний путь.

### Mailpit и настройки

[Mailpit v1.32.0](https://github.com/axllent/mailpit/releases/tag/v1.32.0) копируется в образ из официального Docker-образа, зафиксированного digest. Стартует до API. SMTP слушает `127.0.0.1:1025` внутри контейнера, веб-интерфейс — `8025`, наружу только на `127.0.0.1:8025`. Relay не настроен: демо-письма не уходят в интернет.

| Переменная | По умолчанию |
|---|---|
| `FSP_SMTP_HOST` | `127.0.0.1` |
| `FSP_SMTP_PORT` | `1025` |
| `FSP_SMTP_SENDER` | `ФСП Оренбург <no-reply@fsp.local>` |
| `FSP_SMTP_TLS_MODE` | `none`; `starttls`, `ssl` — с проверкой сертификата |
| `FSP_SMTP_USERNAME`, `FSP_SMTP_PASSWORD` | не заданы |
| `FSP_MAIL_WORKER_ENABLED` | `true` |

Для настоящего SMTP достаточно поменять переменные окружения.

### Эндпоинты (сессия, только свои уведомления)

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/notifications?unread_only=&limit=&offset=` | лента, новые сверху, `{items, total}` |
| GET | `/notifications/unread-count` | `{count}` для счётчика |
| POST | `/notifications/{id}/read` | 204, повторно тоже 204 |
| POST | `/notifications/read-all` | 204 |

Чужое или несуществующее уведомление → 404. Очередь писем через API не выдаётся.

### Фронт

- **Шапка сайта:** колокольчик со счётчиком у вошедшего пользователя. Лента (8 последних) запрашивается при открытии, внизу — «Все уведомления».
- **Кабинет:** у пункта меню «Уведомления» — `Badge` с числом непрочитанных. Отдельного колокольчика нет. На телефоне полоса остаётся «логотип + меню», у кнопки меню — точка, если есть непрочитанные.
- **Страница уведомлений** (`/cabinet/:role/notifications`, без кабинета — `/notifications`):
  - вкладки «Все / Непрочитанные» в адресе, «Прочитать все»;
  - группы по дням: «Сегодня», «Вчера», «14 октября»;
  - «Показать ещё» и «N из M»;
  - клик по уведомлению отмечает его прочитанным оптимистично и ведёт по ссылке, при ошибке — откат и тост.
- **Счётчик** опрашивается раз в 30 с. Если число выросло, перечитываются лента и `me`: решение по роли сразу открывает кабинет.
- Статус доставки письма пользователю не показывается.

## Часть 2. Журнал действий

### Эндпоинты (только федерация)

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/admin/audit?q=&user_id=&action=&object_type=&date_from=&date_to=&limit=&offset=` | записи, новые сверху, `{items, total}` |
| GET | `/admin/audit/catalog` | `{actions: [{code, label}], objects: [{code, label}]}` — все действия и типы объектов для фильтров |

- `q` — поиск автора по email и ФИО.
- `user_id` — точный автор, кнопка «Все действия пользователя».
- Даты — целые дни по Оренбургу. Обратный диапазон → 422.
- Запись: время, автор `{id, full_name, email}` или `null`, `action` и `action_label`, `object_type` и `object_label`, `object_id`, `payload`, IP.
- Ключи `payload` с паролями, токенами, секретами, cookie и authorization вырезаются рекурсивно. Значения вида `token=…` в строках скрываются.
- Русские названия действий — свойство `AuditAction.label` в `audit/domain/actions.py`, объектов — `AUDIT_OBJECTS` там же. Новое действие добавляется вместе с названием.

### Фронт (`/cabinet/federation/audit`)

- Фильтры слева на `lg`, на телефоне — кнопка «Фильтры» и `Drawer`. Поля: поиск автора, действие, объект, период. Всё в адресе.
- Строка: время, действие, автор, объект. Раскрытие показывает детали:
  - `changes` — таблица «Поле / Было / Стало»;
  - `from` → `to` — смена статуса;
  - причина;
  - ссылка «Открыть», если у объекта есть страница: соревнование, событие, статья, модерация ролей;
  - остальное — компактный JSON, IP, «Все действия пользователя».
- «Показать ещё» и «N из M», четыре состояния данных.

## Готово, когда

- Федерация подтверждает роль → у пользователя уведомление в кабинете и письмо в Mailpit; кабинет открывается без перезахода.
- Верификация, отказ и снятие верификации доходят до организатора письмом, запрос верификации — до федерации в кабинет.
- Одобрение и отклонение заявки доходят до участников и тренера письмом, новая заявка — до организатора без письма.
- Отмена соревнования доходит до участников письмом.
- Инициатор действия не получает уведомлений о себе. Письма уходят только по `EMAIL_TYPES`.
- Сброс пароля приходит письмом, ссылки нет в логах и аудите.
- Счётчик в меню кабинета и колокольчик в шапке сайта; страница уведомлений с группами по дням.
- Журнал: фильтры из `catalog`, поиск автора, детали изменений таблицей.
- Pyright — 0 ошибок, фронт — `prettier`, `tsc`, `eslint`, `build` зелёные, контейнер собирается.

## Проверка на демо

1. `python manage/fsp.py` → сайт, API `:8000`, Mailpit `http://localhost:8025`.
2. Федерация (`federation@example.test` / `Demo1234`) → «Модерация аккаунтов» → подтвердить `judge.pending@example.test`. Войти судьёй: уведомление в ленте, письмо в Mailpit.
3. Организатор запрашивает верификацию → у федерации уведомление. Федерация верифицирует → письмо организатору.
4. Спортсмен подаёт заявку → у организатора «Новая заявка». Организатор одобряет → письмо спортсмену.
5. «Забыли пароль?» на входе → письмо в Mailpit.
6. Федерация → «Журнал действий»: отфильтровать по автору и действию, раскрыть запись с изменениями.
