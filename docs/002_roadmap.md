# Карта реализации бэкенда

Порядок определяется зависимостями данных: каждый этап опирается только на готовые предыдущие. Главная цепочка кейса — `соревнование → заявка → протокол → история → разряд → рейтинг → сборная → отчёты`, — поэтому она идёт первой, а публичный слой (новости, лендинг, дневник) — после неё.

Каждый этап — отдельная ветка (`Имя-NNN`), и в каждом этапе обязательно:
- блок в [001_api_map.md](001_api_map.md) по всем новым эндпоинтам;
- расширение seed демо-данными этого модуля;
- запись значимых действий в аудит;
- замена соответствующих заглушек в `cabinets/*` реальными данными.

## Фундамент

### Этап 1. Каркас и авторизация — *идёт сейчас*
План: [003_Ivan-001_auth.md](003_Ivan-001_auth.md).
Docker, `core/`, пользователи и роли, сессии, CurrentUser, восстановление пароля, верификация ролей, аудит, кабинеты-заглушки, демо-аккаунты.
**Готово, когда:** регистрация → верификация федерацией → доступ к кабинету → выход → сброс пароля проходят через Swagger.

### Этап 2. Справочники — *готово (Ivan-002), [004_tz_dictionaries.md](004_tz_dictionaries.md)*
От них зависят все остальные модули, поэтому они идут первыми после авторизации.
- Таблицы: `disciplines`, `age_groups` (границы по возрасту), `academic_groups` (классы / студенты), `municipalities`, `organization_types`, `contest_types`, `contest_levels`, `contest_formats`, `rank_types` (min_age, validity_months, is_lifetime, valid_until_age), `judge_categories` (validity_months), `judge_positions`.
- Эндпоинты по каждому справочнику: публичное чтение, для федерации — создание, правка, удаление, архив и восстановление записей. Подробно — [004_tz_dictionaries.md](004_tz_dictionaries.md).
- Seed: 6 дисциплин из кейса + «Квизы», разряды и сроки по ТЗ, категории судей, муниципалитеты области.

**Готово, когда:** федерация правит любой справочник, и никакие возрасты, сроки или баллы не зашиты в код.

### Этап 3. Уведомления (ядро) и файлы — *уведомления и журнал: [006_tz_notifications_audit.md](006_tz_notifications_audit.md)*
Это сквозная инфраструктура: её вызывают почти все следующие модули, поэтому делаем её до них.
- `notifications` + `NotificationService.notify(user_id, type, payload)` для доменов других областей. `GET /notifications`, `POST /notifications/{id}/read`, `POST /notifications/read-all`.
- Email: отправка через SMTP фоновой задачей с повторами; в контейнере — Mailpit или вывод в лог. Сюда же переводим ссылку сброса пароля.
- `files` — вынесено в параллельную ветку вместе с новостями, хранение в MinIO: [005_tz_files_news.md](005_tz_files_news.md).

**Готово, когда:** любой домен одной строкой шлёт уведомление в кабинет и на почту; файл загружается и отдаётся только тому, кому можно.

## Главная цепочка

### Этап 4. Профили и реестр
- Поля профилей: спортсмен (муниципалитет, организация, дисциплины, год начала занятий), тренер, судья. Законный представитель для несовершеннолетнего.
- `organizations` + организации, к которым привязан человек.
- Периодические связи с `valid_from / valid_to` (организация, дисциплины) — без них не посчитать динамику численности на этапе 13.
- `GET/PATCH /me/profile/{role}`, реестр `GET /registry/athletes|coaches|judges|organizations` с фильтрами и пагинацией (федерация), `GET /admin/audit`.

**Готово, когда:** федерация ищет спортсмена по дисциплине, разряду, возрастной группе, муниципалитету, организации.

### Этап 5. Тренер ↔ спортсмен
- `coach_athlete_links` + история: `requested → active → suspended → ended`, дисциплина у связи, несколько тренеров по разным дисциплинам.
- Тренер ищет спортсмена и шлёт запрос, спортсмен подтверждает. Уведомления обеим сторонам.

**Готово, когда:** у тренера в кабинете реальный список подопечных.

### Этап 6. Соревнования — *Ivan-003, [007_tz_contests.md](007_tz_contests.md)*
- `contest_requests`: организатор подаёт заявку → федерация согласует или отклоняет с причиной.
- `contests`: все поля из спецификации 5.5, возрастные ограничения, положение (файл), окно регистрации, номер в ЕКП / КП.
- Статусы `draft → published → registration_open → registration_closed → in_progress → results_entered → protocol_published → archived` (+ `cancelled`), переходы с проверками и историей.
- Публичный календарь `GET /contests` с фильтрами; федерация может создать соревнование сама.

**Готово, когда:** организатор → заявка → согласование → соревнование в публичном календаре.

### Этап 7. Заявки на участие — *Ivan-005, [010_tz_applications.md](010_tz_applications.md); согласие для < 18 — отдельной веткой*
- `applications` + история: подаёт спортсмен или его активный тренер.
- Проверки на сервере: окно регистрации, возраст и категория на дату начала, запрет дубликата, согласие для < 18.
- Генерация PDF согласия для родителя → загрузка скана → федерация отмечает «согласие проверено».
- Модерация: одобрить / отклонить с причиной, отзыв заявки. Уведомления.

**Готово, когда:** несовершеннолетний не может подать заявку без скана согласия, а неподходящий по возрасту — вообще.

### Этап 8. Судьи
- `judge_category_records`, `judge_category_applications` → решение федерации → срок действия по справочнику.
- `judge_assignments`: состав коллегии соревнования с должностями; назначить можно только судью с действующей на дату соревнования категорией.

**Готово, когда:** у судьи в кабинете реальные категория, заявка и назначения.

### Этап 9. Результаты и протокол
- Ввод результатов только по одобренным заявкам; ранжируются все участники, ничьи `1, 2, 2, 4`, дисквалификации.
- Сущность **«занятое место»**: снимок на дату соревнования — спортсмен (или команда и её участники), соревнование, дисциплина, место, баллы по `rating_points` соревнования, возрастная группа по дате рождения, академическая группа из профиля, муниципалитет, организация, разряд, уровень, верифицировано ли. История не пересчитывается при изменении профиля.
- `protocols` с версиями: исправление = новая версия.
- Генерация протокола `.docx` и `.pdf` из данных (шрифт с кириллицей в Docker).
- Публикация запускает цепочку: история выступлений спортсмена → сводка тренера → уведомления. Хук для пересчёта рейтинга закладываем сразу, наполняем на этапе 11.

**Готово, когда:** сквозной сценарий чекпоинта № 2 проходит до протокола и истории. **Это минимум для чекпоинта № 1.**

### Этап 10. Разряды и контроль сроков
- `rank_records` (привязка к результату-основанию, приказ, дата, срок по справочнику, юношеские до 18 лет), `rank_applications` от спортсмена или тренера → решение федерации.
- Подсветка возможного разряда по правилам `evsk_rules` при публикации протокола.
- Deadline Engine: APScheduler в монолите, блокировка в Redis, пороги из `core/config.py`, `deadline_notices` против повторов. Следит за окнами регистрации, разрядами, категориями судей.

**Готово, когда:** спортсмен видит срок разряда и получает предупреждение об истечении.

### Этап 11. Рейтинг
- Считается из «занятых мест» только верифицированных соревнований; баллы за места — из настройки соревнования при верификации (см. [007](007_tz_contests.md)).
- Разные способы расчёта поверх одних и тех же снимков: сумма, средневзвешенное, по возрастной или академической группе, окно 12 месяцев / сезон.
- `rating_rules` с версиями (коэффициент 1,2, окно), `rating_snapshots`, `rating_entries` с расшифровкой.
- Пересчёт при публикации или исправлении протокола и при смене правил; идемпотентный; кэш в Redis.
- Исключение дисквалифицированных и отстранённых. `GET /ratings`, `GET /ratings/{athlete}/explain`.

**Готово, когда:** пример из спецификации (40 + 45 + 0 → 102) воспроизводится на демо-данных.

### Этап 12. Сборная
- `squads`, `squad_members`: предложение топ-N из рейтинга → ручная правка с комментарием → `draft → approved → published → archived`, изменение утверждённого = новая версия.
- Предупреждения: отстранение, истёкший разряд, неполный профиль.
- Проект приказа `.docx`.

**Готово, когда:** федерация собирает сборную по дисциплине и категории и скачивает приказ.

### Этап 13. Отчёты xlsx
- Динамика численности ≥ 2 года по периодическим связям, с дедупликацией, разрезы: организация, дисциплина, возрастная группа, муниципалитет.
- Рейтинги, протоколы, отчёты по спортсмену / судье / организатору / тренеру.

**Готово, когда:** все выгрузки скачиваются и не пустые. **Минимум для чекпоинта № 2.**

## Публичный слой

### Этап 14. Справки с QR
`certificates` (номер, снимок данных, токен, статус), PDF с QR, публичная `GET /verify/{token}` без лишних ПДн, аннулирование.

### Этап 15. Новости — *параллельная ветка, [005_tz_files_news.md](005_tz_files_news.md)*
`news_articles` с блоками в JSONB, хэштеги, черновик / опубликовано, просмотры в Redis со сбросом в БД и защитой от накрутки. Публичная лента без входа.

### Этап 16. Лендинг (API)
Агрегирующие публичные эндпоинты: ближайшие соревнования, топы рейтингов, последние новости, внешний календарь (iCal с кэшем в Redis).

### Этап 17. Дневник спортсмена
`athlete_diary_entries` с фото и заметками к участиям, модерация федерацией, публичная страница `/athletes/{slug}` с управлением видимостью и ограничениями для несовершеннолетних.

### Этап 18. Codeforces и соцсети
Привязка handle с подтверждением владения, периодический опрос API Codeforces, кэш, показ последнего значения при недоступности. Ссылки на соцсети с валидацией.

## Финиш

### Этап 19. Демо-данные и сдача
Добивка seed до требований спецификации (раздел 14), README (запуск, демо-аккаунты, сценарии проверки), проверка чистого запуска.

### Этап 20. P2 — только при запасе времени
Документы о судействе, «что нужно для следующего разряда», страница показателей, апелляции, API-токены + вебхук.

## Что можно вести параллельно

После этапов 1–3 работа расходится на три независимые дорожки:

| Дорожка | Этапы | Комментарий |
|---|---|---|
| A — соревнования | 6 → 7 → 9 | критический путь, сюда самые сильные руки |
| B — люди | 4 → 5 → 8 → 10 | этап 10 ждёт 9 (результат-основание разряда) |
| C — публичное | 15 → 16, 14 | почти не зависит от остального; 14 ждёт 9 |

Дальше 11 → 12 → 13 идут после слияния A и B; 17 и 18 — после 4.
